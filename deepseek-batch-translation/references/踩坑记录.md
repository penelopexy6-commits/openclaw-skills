## 孤儿进程覆盖产物 🔥（P0 通用）

**背景：** 2026-07-31 翻译任务完成（缺失 0）后，文件被旧进程覆盖成“全翻译缺失”。

**现象：** 正确文件（242KB）写入后，Obsidian 里变成全缺失（145KB）
**原因：** 启动多个翻译进程，`kill <bash父进程>` 只杀了 bash，python 子进程成孤儿继续跑；几十分钟后它写完“全缺失”结果，覆盖了正确文件。同时清理临时文件时误删了完整翻译缓存（/tmp），结果全丢。
**解法：**
- 杀进程用 `pkill -f <关键词>`（杀整棵进程树），杀完 `ps aux | grep` 验证无残留
- 重要产物完成后立即验证（grep 缺失计数）+ 尽早 git commit
- 临时缓存（/tmp）别急着删，确认产物验证过再清

## DeepSeek 批量翻译三连坑 🔥（P0 通用）

**背景：** 2026-07-31 翻译 1106 段 Karpathy 视频转录（中英对照），首版 27 分钟白跑 + 两轮返工。

**坑1：reasoning 模型大批次返回空内容**
- 现象：`deepseek-v4-flash`（reasoning 模型）翻译 4 个标题正常，30-40 段批次时 content 返回空 → 整批缺失
- 原因：reasoning 模型先输出思考过程，吃光 max_tokens 预算 → 最终答案空
- 解法：批量翻译必须用非 reasoning 模型（`deepseek-chat`），速度还快 3-5 倍

**坑2：批内序号覆盖全局序号**
- 现象：翻译全部错位（[00:00] 显示的是别的段的内容）
- 原因：translate_batch 返回批内序号(0-39)，写文件用全局序号查 → 后批覆盖前批
- 解法：缓存 key 一律用全局索引，批内序号只用于单批内映射

**坑3：没先验就全量跑**
- 现象：27 分钟全量跑完才发现错位/缺失
- 解法：先 `--verify` 跑 10 段核对序号对应关系，再全量

**其他：**
- json 缓存 int key 变 str → 加载时 int(k) 转换；章节标题 key 用 `chap_<i>` 前缀区分
- 写文件查缓存用全局索引，别用元组/复杂表达式当 key
- 模型输出解析丢失是常态（约 10%），必须有补翻循环
